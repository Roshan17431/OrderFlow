# Infrastructure image release pins

Cloud Compose requires `INFRA_IMAGE_CADDY`, `INFRA_IMAGE_KAFKA`, `INFRA_IMAGE_NODE_EXPORTER` and `INFRA_IMAGE_GRAFANA` without fallback values. Local maintained builds and their config IDs do not authorize registry publication or deployment. **Infrastructure publication and cloud deployment: NOT RUN.** No populated `deploy/infrastructure-images.json` is supplied by this remediation.

After separate authorization to publish reviewed images, an operator must select immutable publication tags in the existing twelve `orderflow/<service>` ECR repositories in the release account and region. Review that choice against the existing application publication tags; do not create a repository or overwrite an application tag. Allowed repository suffixes are `service-registry`, `api-gateway`, `auth-service`, `product-service`, `cart-service`, `inventory-service`, `order-service`, `payment-service`, `delivery-service`, `notification-service`, `operations-service` and `frontend`. AWS Mumbai resources and the application release schema remain unchanged.

Use [the placeholder template](../deploy/infrastructure-images.example.json) only after that authorized publication. Prepare reviewed JSON for the exact release: `releaseVersion`, full `gitSha`, account, region, environment and platform must match the selected workflow target and eventual `deploy/release-manifest.json`. Its `images` must contain exactly `caddy`, `kafka`, `node-exporter` and `grafana`, each with only `uri` and `digest`. Every URI must be a same-account, same-region allowed ECR repository followed by `@sha256:<64 lowercase hex>`, matching its digest field. Tags, other repositories, extra/missing fields and mismatched release metadata are rejected. The existing application manifest stays schema version 1 with exactly twelve application images.

Obtain each digest from the published registry manifest. Never insert a local Docker image/config ID into a registry URI as if it had been published. Offline syntax and target validation cannot distinguish those two kinds of SHA256 value and cannot prove registry existence, provenance or scan approval. Separate publication review must bind each published artifact to its tested build and scan evidence. On an authorized deployment, image pulling must succeed, and tooling checks each infrastructure image's `RepoDigests` for the exact frozen URI and checks its OS/architecture against the release platform. Those registry/runtime checks have only mocked coverage in this local remediation.

The release tooling loads the frozen infrastructure file from that release's source directory and injects its four references over ambient variables and `runtime.env`. Do not use runtime settings to select a different infrastructure build. Old rollback archives whose Compose contains fixed vendor references remain readable without the new file; this compatibility does not approve an old vulnerable image for a new deployment.

Once the final source SHA is known and the separate infrastructure publication review is complete, manually dispatch **Build immutable release images** for that exact source revision and provide the nonsecret JSON through its optional `infrastructure_images_json` string input. Reusable callers can supply the same input. Alternatively, an authorized operator can set `APPROVED_INFRASTRUCTURE_IMAGES_JSON` on the protected `cloud-demo-publish` environment for that exact SHA; the existing **Release** wrapper can use this fallback. The explicit input takes precedence. Keep credentials and runtime secrets out of this metadata. Existing environment approval and authenticated account controls remain required.

The workflow passes this JSON through an environment value and parses it as data in Python. Before obtaining AWS credentials, it rejects absent/malformed input and validates the full `GITHUB_SHA`, account, region, release, platform and four strict image records. A stale checkout file never supplies approval. It then generates frozen `deploy/infrastructure-images.json` and packaging includes it in the archive. Do not commit the populated file: a file containing its own commit's final SHA would be self-referential. After a new commit, prepare newly approved matching JSON and dispatch again; a rerun uses its original inputs, so update the protected fallback first when relying on that route. Automatic/reusable runs without matching approved metadata fail closed. The example is intentionally invalid deployment input.

Packaging validates the completed archive before upload. Every new archive using these Compose slots must contain a regular, nonempty infrastructure manifest bound to its embedded application manifest. The archive checksum therefore freezes both manifests together. For offline review of an already prepared bundle, run:

```sh
python3 scripts/deploy/cloud.py validate-artifact \
  --manifest deploy/release-manifest.json --artifact deploy/release.tar.gz
```

This command performs no AWS, image pull or deployment operation. Standalone Compose configuration checks must explicitly supply the same approved `INFRA_IMAGE_*` values; local tests use clearly synthetic references and never claim they exist in ECR.
