# Cloud runtime configuration

OrderFlow runs on one Ubuntu 24.04 EC2 instance with encrypted persistent EBS mounted at `/opt/orderflow`. This portfolio configuration is not highly available. PostgreSQL, Kafka, Redis and the host each remain a single point of failure; releases can interrupt requests and streams.

Cloud Java heaps are capped at 50% of container memory to reserve native/metaspace/thread/code memory. Registry is 320 MiB; gateway/auth/product/cart/operations are 640 MiB each; inventory/order/payment/delivery/notification are 1 GiB each. All configured container limits, including infrastructure and monitoring, total 12.5 GiB, leaving 3.5 GiB of the proposed 16 GiB host for the OS/cache and runtime reserve. The effective Compose policy checks this total and per-JVM native reserve. These budgets still require workload measurements on the approved host; they do not prove EC2 capacity.

Use Docker Compose 2.24.4 or later. The cloud override deliberately **replaces** environment maps and clears every inherited application build and host port. A single-file cloud invocation is unsupported:

```sh
docker compose --env-file /opt/orderflow/config/runtime.env \
  -f docker-compose.yml -f docker-compose.cloud.yml config --quiet
```

Use `config --quiet` when real secrets exist; ordinary `config` prints resolved credentials. Twelve application image variables in `infrastructure/cloud/runtime.env.example` must reference account/region-matching ECR repository URIs with `@sha256:<64 hex>`. Release tooling verifies the manifest; Compose interpolation alone does not establish that a string is an immutable digest. Build frontend images with `NEXT_PUBLIC_API_BASE_URL=`; API request paths already include `/api`, and an empty base uses the public HTTPS origin. Public frontend build settings cannot carry secrets.

Populate `config/runtime.env` using scoped SSM Parameter Store retrieval. Keep its directory mode 0700 and file mode 0600, owned by root. Environment credentials are visible to privileged host/Docker administrators; SSM, IAM and root access form the security boundary. Never print the resolved manifest or runtime environment into CI or a terminal recording. Persistent volumes map onto `/opt/orderflow/data/{postgres,redis,kafka,caddy,prometheus,grafana}`. Secrets, releases, backups and signing keys are also on persistent EBS. No local development data is imported.

`POSTGRES_USER`/`POSTGRES_PASSWORD` are a separate administrator identity, with maintenance database `postgres`. Eight distinct `AUTH`, `PRODUCT`, `INVENTORY`, `ORDER`, `PAYMENT`, `DELIVERY`, `NOTIFICATION` and `OPERATIONS_POSTGRES_{DB,USER,PASSWORD}` values define database owners. Auth receives its dedicated credentials through its existing `POSTGRES_*` application interface. The cloud bootstrap creates missing databases, enforces non-superuser roles, removes public database access and schema CREATE, and refuses mismatched existing ownership. It never drops data or silently takes over an existing database. Owner credentials run Flyway only in their own database. Password rotation of the initialized Postgres administrator requires an explicit SQL rotation; changing `POSTGRES_PASSWORD` does not change an existing database role.

Redis requires a password, AOF with `appendfsync everysec`, bounded 256 MiB memory and `noeviction` so session revocation does not silently disappear under eviction. Kafka uses persistent KRaft storage, a stable `KAFKA_CLUSTER_ID`, private broker/controller listeners, seven-day/one-GiB-per-partition retention, and replication factor one. Do not change the cluster ID of existing storage. Encrypted EBS protects storage at rest; internal Docker traffic is plaintext within the host trust boundary. Measure retention and capacity before relying on this topology.

Only Caddy publishes public 80/443. Prometheus and Grafana are optional `observability` profile services bound to host loopback; credentials remain mandatory at parse time even when that profile is off. All other containers have no published host ports. Docker bridge networks permit controlled outbound access for ACME/OAuth; they do not publish service listeners. Security groups must independently allow only 80/443 inbound. Caddy targets the gateway through the edge-only `api-gateway-edge` DNS alias, preventing the private network address from bypassing the configured physical-peer trust. Caddy has fixed edge address `172.31.250.2` in `172.31.250.0/24`; gateway trusts only that physical peer. If this subnet conflicts with an existing network, change the subnet, Caddy address, gateway trusted address and trusted-proxy regex together, then rerun proxy and gateway tests before releasing.

Place matching RS256 PEMs at `config/jwt-private.pem` and `config/jwt-public.pem`. Provision or retrieve them once; deployment must never regenerate them. The auth image explicitly runs as UID/GID 10001: use root-owned 0700 parent directory, UID 10001 owned 0400 key files, and read-only single-file mounts. Verify the actual released image UID during preflight; if it differs, adjust only these files explicitly before starting auth. Compose refuses missing key sources and disables ephemeral keys. Never mount the whole config directory. Use a stable `APP_JWT_KEY_ID`; key rotation requires documented JWK overlap and token-expiry/revocation planning, not replacement during every restart. See ADR 0035.

The cloud profile is `docker,cloud-demo`; payment and notification adapters are simulators. `APP_PAYMENT_DEMO_COMPLETION_ENABLED=true` enables a backend-held signed demo completion worker. The browser never obtains the signing secret. The payment secret is required; true production profiles reject simulator convenience. OAuth is optional: activate `docker,cloud-demo,oauth2` only after configuring both supported provider registrations and exact public callbacks. Refresh cookies are Secure and keep their existing HttpOnly, CSRF and Strict SameSite protections. Bootstrap admin creation is disabled.

Host bootstrap requires `EBS_VOLUME_ID`, `EBS_ENCRYPTION_VERIFIED=true` established from the encrypted EBS definition/read-only AWS inspection, and explicit `ALLOW_FORMAT_EMPTY_VOLUME=true` for a new empty device. It resolves the exact NVMe EBS serial, refuses existing partitions, unknown signatures, conflicting mounts and nonempty mount directories, and only creates ext4 on an explicitly authorized blank volume. Existing ext4 storage is mounted by UUID without formatting. Inspect legacy partitioned volumes manually; bootstrap deliberately stops instead of guessing. It installs Docker, SSM, official AWS CLI v2 through the AWS-supported signed Snap Store package, bounded log rotation, time sync and unattended security updates without rebooting. The `orderflow` account has no Docker group; audited SSM sudo provides deployment access. Docker daemon setting changes take effect on the next approved restart; bootstrap does not interrupt existing containers.

Local verification:

```sh
python3 -m unittest discover -s infrastructure/cloud/tests -v
python3 infrastructure/cloud/tests/proxy_integration.py
python3 infrastructure/cloud/tests/database_integration.py
bash -n infrastructure/bootstrap/bootstrap-ec2.sh
sh -n infrastructure/bootstrap/bootstrap-databases.sh
```

The last two integration commands create temporary named containers only. They remove their own containers and temporary test data, never existing application volumes. Bootstrap installation/mount operations have not been executed on real Ubuntu/EBS by these checks.

AWS CLI bootstrap selects amd64/arm64 through snapd, requires signed store assertions (no unsigned sideloading), validates `aws-cli/2` execution and retains an existing valid CLI. Snap updates track the official stable package; this installation method does not pin a minor CLI version. Existing CLI v1 or conflicting paths require operator review. See the [official AWS CLI snap installation instructions](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html#install-linux-snap). No AWS credentials are created or written by bootstrap.

## Controlled demo accounts and verification

The deployed verification hook is `scripts/cloud/verify-journey.sh`. It makes actual synthetic application writes only after `ORDERFLOW_CLOUD_E2E=true`, `ORDERFLOW_TARGET_ENVIRONMENT=cloud-demo` (or an explicitly authorized `staging`), a twelve-digit `AWS_ACCOUNT_ID`, and a plain `ORDERFLOW_PUBLIC_URL=https://<owned-domain>` are supplied. Public verification uses the standard trusted CA store. Redirects are refused rather than forwarding fixture credentials. There is no production target mode and no `--insecure` option.

The operator provisions `config/cloud-accounts.json` through the deployment-scoped SSM SecureString `runtime/cloud-accounts.json`. Its directory is root-only; its file is mode0600 owned by the verification process user. `ORDERFLOW_CLOUD_ACCOUNTS_FILE` selects that file. Exact JSON schema:

```json
{
  "VENDOR": {"email": "demo-vendor@example.test", "password": ""},
  "DELIVERY_AGENT": {"email": "demo-agent@example.test", "password": ""},
  "ADMIN": {"email": "demo-admin@example.test", "password": ""}
}
```

Replace each empty value with a separately generated 16–128 character secret through the protected operator workflow; never commit the populated file or print it. Only distinct fake `@example.test` identities are accepted. Normal API registration assigns CUSTOMER; privileged roles are never granted through a public endpoint. Operator accounts must already hold their intended roles before the release verification hook starts.

For first-time **explicitly authorized** seeding on the trusted EC2 host, use `scripts/cloud/seed-demo.sh --dry-run` followed by `scripts/cloud/seed-demo.sh`. Both require the cloud target gates plus `ORDERFLOW_DEMO_SEED=true` and `ORDERFLOW_TRUSTED_HOST_ROLE_GRANT=true`. `ORDERFLOW_RUNTIME_ENV_FILE` defaults to `/opt/orderflow/config/runtime.env`; its account, environment and domain must match the HTTPS target. `ORDERFLOW_COMPOSE_PROJECT_NAME` defaults to `orderflow-cloud` and may select an explicitly isolated local simulation project. Dry run validates protected files and matching configuration without network/SQL execution.

Seeding registers/logs in only the three supplied fake accounts through normal auth APIs, validates canonical UUIDs and matching email identities, then uses trusted host `docker compose exec` SQL to grant only VENDOR, DELIVERY_AGENT or ADMIN to those exact ACTIVE rows. PostgreSQL credentials remain in the private container and are not passed on argv. Each role token is minted by a fresh normal login. A host file lock prevents concurrent seed runs. The seed creates one stable synthetic category, one vendor-owned product and initial stock only when the product is new; reruns do not reset existing stock, product status, credentials, roles or unrelated data. A partially completed initial seed can leave a draft/empty-stock fixture requiring explicit operator review; it does not silently replenish stock. The agent profile stays offline. No customers, orders, payments or real deliveries are seeded automatically.

The verification journey generates a unique CUSTOMER plus unique category/product/cart/order data, checks idempotent order creation, observes simulator PROCESSING before the backend-held signed worker reaches PAID, and completes only that synthetic delivery through the dedicated agent. It refuses a busy operator agent, an already assigned fixture delivery, other pending deliveries or an order list too large to establish exclusive assignment safely. Run during a quiet dedicated demo/staging window: agent availability automatically assigns the oldest pending delivery, so concurrent unrelated order traffic is incompatible with this check. Failed runs retain their synthetic data for inspection; no data reset or business-data cleanup occurs.

The journey also checks Secure/HttpOnly/Strict refresh cookies, Secure CSRF cookies, missing-CSRF rejection, refresh-cookie rotation, unauthorized/foreign ownership denial, blocked public internal paths, actual authenticated SSE notification content tied to the customer list, operations projections and Redis-backed logout revocation. SSE carries bearer authorization in its header and no token in the URL. Reports contain only synthetic UUIDs, aggregate gate results and timings, never passwords/tokens/cookies; `ORDERFLOW_JOURNEY_REPORT` may select a new output path but an existing file is never overwritten.

Private monitoring is mandatory for this verification hook: set `ORDERFLOW_PROMETHEUS_URL` to the actual private literal RFC1918 container address from trusted host inspection, or a loopback SSM-forwarded endpoint. URLs with public hostnames, credentials, paths or queries are rejected. All eleven application scrapes and process-start metrics must be present, healthy and recently sampled; the final metrics check waits for every service to be scraped after operations completion so stale zero values cannot establish PASS; all five actual outbox-publication services must expose backlog/failed gauges. Failed outbox records or any recorded DLT publication fail the hook, and the final outbox backlog must drain to zero. The current Java DLT counters are created lazily on first publication: absent counters mean zero publications in a healthy unchanged process lifetime. This check does **not** prove persisted DLT Kafka topics are empty across prior restarts; inspect topic offsets privately when recovering historical DLTs. A service restart during verification invalidates counter evidence and fails the hook. Admin operations overview alone has no outbox/DLT fields and cannot replace these gates.

For a **separately identified local TLS simulation**, add `ORDERFLOW_LOCAL_TLS_TEST=true`, use only `https://localhost:<port>` or `https://127.0.0.1:<port>`, and provide `ORDERFLOW_CA_FILE` with the explicit locally generated CA certificate. Certificate verification remains enabled, and reports clearly say local simulation. This override is rejected for public domains; local results never establish AWS/DNS/public ACME success.

`scripts/cloud/performance-smoke.sh` adds `ORDERFLOW_PERFORMANCE_SMOKE=true` to the same target gates. It samples only the public frontend and catalog, defaults to twelve requests/concurrency two, and strictly caps `ORDERFLOW_PERFORMANCE_REQUESTS` at thirty and `ORDERFLOW_PERFORMANCE_CONCURRENCY` at two. Ten-second requests bound execution; any HTTP/TLS/body failure prevents a PASS. Output reports actual p50/p95/p99 and error count. This is an availability/timing smoke sample, not a capacity benchmark or production latency guarantee.

Offline safety validation:

```sh
python3 -m unittest discover -s scripts/cloud/tests -v
python3 -m py_compile scripts/cloud/*.py
bash -n scripts/cloud/verify-journey.sh
bash -n scripts/cloud/seed-demo.sh
bash -n scripts/cloud/performance-smoke.sh
```

Mocked failure tests establish rejection/timeout/no-overwrite behavior only. Complete cloud journey, public TLS and cloud performance remain NOT RUN until account/domain access and explicit deployment/test authorization exist.

## Reproducible local TLS preparation

`python3 infrastructure/cloud/tests/prepare_full_stack.py` creates a fresh private `/tmp/orderflow-phase10-local-*` fixture and prints only paths and commands. It generates dummy runtime credentials, unique fake operator emails/passwords, matching PKCS8 RSA PEMs and a local-only Compose overlay for twelve `orderflow/<service>:phase10-local-amd64` application images. Use `--application-platform linux/arm64` with explicitly built `phase10-local-arm64` tags for native application testing on Apple Silicon. This local platform choice does not change the AWS release target or prove its capacity. The helper does not build, start or stop the application. The optional `--prepare-permissions` action runs one bounded, network-disabled permission container against only that newly created directory; keys become UID/GID10001 mode0400, and fresh data mount directories get their actual image UIDs. No existing user path or volume is mounted into the permission container.

The test overlay uses 128 MiB JVM heaps, 384 MiB Java container limits, 512 MiB for order and inventory, 224 MiB for the registry and 256 MiB for the frontend. Java services use the default optimizing JIT. On this 8 GiB Mac/4 GiB Docker VM, AMD64 emulation and extended native runs exhausted memory; later browser requests also caused an inventory OOM. Temporarily pausing optional monitors and a bounded experiment with smaller JVM native limits did not establish a reliable complete journey. The experimental JVM flags were not retained in the helper. The helper produces test configuration, not a promise that the full stack fits a 4 GiB VM. Allocate sufficient resources on the explicitly selected test host and keep failed fixtures for inspection. It uses native ARM Kafka infrastructure, loopback Caddy8443/18080 and observability19090/19001, and explicit Caddy `tls internal`. These limits and locally trusted certificates are test settings; they do not change cloud budgets or establish public HTTPS/capacity readiness. Docker Desktop local testing uses direct host bind mounts because cloud local-driver EBS device paths refer to the Linux VM filesystem. macOS file-sharing ownership can be virtualized: the helper creates local PEMs host mode0600 under a private0700 parent so the permission container can apply guest UID/GID10001 mode0400. The macOS host can continue showing current-user ownership/mode0600 while the actual auth bind mount shows10001:10001/0400. Inspect the released auth container's mounted stat/readability before claiming permission validation. Native Ubuntu/AWS uses actual POSIX ownership10001 and mode0400; this local preparation change does not relax the cloud key policy. The local node-exporter overlay omits rslave propagation because Docker Desktop's root mount is not shared; the Linux cloud mount retains rslave. Kafka native3.9.1 has no JVM CLI scripts, so the local-only healthcheck sends a bounded read-only Kafka ApiVersions request and validates its correlation ID, success code and API list; the cloud Java Kafka image retains its real topics-CLI healthcheck.

Each fixture includes a private `fixture.json` containing its exact Compose/ownership commands and paths without secret values. After an explicitly selected isolated stack starts, extract its local CA certificate to the printed path, then supply the printed local-only gates to `seed-demo.sh`, `verify-journey.sh` and the separately opted-in performance smoke. Preparation and successful Compose parsing do not prove the full stack or business journey works. Preserve failed synthetic fixtures for investigation; the helper never deletes volumes or application data.
