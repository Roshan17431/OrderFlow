# Cloud CI/CD

The active workflows are in the Git root `.github/workflows`, one level above the Maven project. No remote workflow has run as part of local preparation. Publication and deployment require the user to push reviewed code and approve the configured GitHub environments.

| Workflow | Responsibility | Approval and identity |
| --- | --- | --- |
| `ci.yml` | Complete Java 21 `clean verify`, security/dependency scans, SBOM, frontend lint/types/tests/build/fixture browsers, twelve image builds, monitoring, Terraform fmt/init/validate and mocked plan tests, cloud policy/automation/journey safety tests, actual local TLS transport, Caddy validation, cloud Prometheus rule validation, shell syntax, actionlint | Read-only; PRs/main/master |
| `build-images.yml` | Reuses CI once, builds twelve version+full-SHA images for an explicit platform, verifies immutable ECR repositories, publishes and produces a digest manifest/source bundle | `cloud-demo-publish`, publish role only |
| `release.yml` | Calls build-images, leaves an explicit manual deployment handoff | Same publication approval; no automatic deployment |
| `deploy.yml` | Manual dispatch downloads a successful trusted release artifact, validates checksums/target, transfers through private S3 and waits for SSM deployment result | `cloud-demo`, separate deploy role |

Reusable release CI skips only duplicate image builds. All backend/frontend/security gates stay enabled; the publication job then builds all twelve images once. Dockerfile packaging may skip Maven tests because the complete verification gate has already passed. Frontend builds use an empty public API origin for same-origin `/api/...` calls. Secret values never enter build arguments, artifacts, public environment variables or release manifests.

Configure these GitHub **environment variables**, using actual Terraform outputs and the approved DNS name:

- Both environments: `AWS_ACCOUNT_ID`, `AWS_REGION`, `DOMAIN_NAME`.
- `cloud-demo-publish`: `AWS_PUBLISH_ROLE_ARN`, optional `NEXT_PUBLIC_OAUTH_PROVIDERS`.
- `cloud-demo`: `AWS_DEPLOY_ROLE_ARN`, `AWS_INSTANCE_ID`, `AWS_ARTIFACT_BUCKET` (Terraform `release_bucket`).

Require reviewers, prevent self-approval where supported, and restrict environments to the reviewed default branch. This is operationally necessary: AWS trust checks the environment subject, while GitHub environment protection restricts the allowed branch. OIDC subjects are exactly `repo:Roshan17431/OrderFlow:environment:cloud-demo-publish` and `repo:Roshan17431/OrderFlow:environment:cloud-demo`, audience `sts.amazonaws.com`. No static AWS access key is required. See [GitHub's AWS OIDC guide](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

Publish repositories are `orderflow/<service>` in the approved account/region, with immutable tags `<vMAJOR.MINOR.PATCH>-<full Git SHA>`. Manifests contain `@sha256:` references; runtime does not deploy floating tags. Explicit migration hashes and a reviewed `backwardCompatible` boolean accompany the complete image set. SQL migrations remain append-only. A reviewed false flag permits a forward migration, but blocks reverting application images afterward.

Dispatch **Release** or **Build immutable release images**, choosing the target platform that matches EC2. After its publication approval and successful completion, record its run ID. Dispatch **Deploy approved cloud demo release** with the same release version and run ID, then approve `cloud-demo`. The workflow verifies the artifact producer is a successful workflow in `Roshan17431/OrderFlow`, validates the external manifest and archive checksum, checks STS account identity, uploads an SSE-encrypted object under `releases/`, and sends an `AWS-RunShellScript` invocation only to the configured instance.

The instance role retrieves artifacts and five decrypted parameters under `/orderflow/cloud-demo/runtime/`: `runtime.env`, `jwt-private.pem`, `jwt-public.pem`, `backup.key`, `cloud-accounts.json`. The secret directory is 0700, runtime/key files 0600, and JWT bind-mount files 0400 owned by the auth UID/GID 10001. Existing JWT or backup keys must match SSM; fetch refuses implicit rotation. Provision parameter values separately from Terraform. See `infrastructure/cloud/runtime.env.example` and [secret management](secrets-management.md).

SSM polling has a finite deadline. Success requires invocation `Status=Success` **and** `ResponseCode=0`; failed/cancelled/timed-out statuses fail the workflow. Private command output is suppressed. A client timeout leaves remote state uncertain: inspect the specific invocation before retrying. This follows the distinction in [AWS GetCommandInvocation](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_GetCommandInvocation.html).

A filesystem lock serializes host deployments. `healthy.json` and `previous.json` change only after full readiness, registration, HTTPS checks and the deployed journey hook succeed. `schema-release.json` is recorded before migrations may run, so a failed candidate still constrains rollback. Failed releases never trigger automatic database restore. See [deployment](runbooks/cloud-deployment.md) and [rollback](runbooks/cloud-rollback.md).

Local safety tests and YAML/actionlint checks are evidence of configuration behavior. They do not prove AWS OIDC, ECR publishing, SSM, public TLS or deployed browsers. Report all remote execution as **NOT RUN** until an approved environment actually executes it.

Journey hook inputs include `ORDERFLOW_PUBLIC_URL`, `ORDERFLOW_CLOUD_E2E=true`, `ORDERFLOW_TARGET_ENVIRONMENT=cloud-demo`, the explicit `AWS_ACCOUNT_ID`, and `ORDERFLOW_CLOUD_ACCOUNTS_FILE=/opt/orderflow/config/cloud-accounts.json`. The latter is protected JSON keyed by `VENDOR`, `DELIVERY_AGENT`, `ADMIN`, each with `email` and `password` (distinct fake `@example.test` addresses, passwords of 16–128 characters). Missing authorized demo accounts fail verification. Private Prometheus is reached at its inspected internal Docker IPv4, not a public or host-published endpoint.

The archive is checked before S3 transport: its embedded manifest must match the external one, SQL hashes must match, required runtime files must exist, and unsafe archive paths/links/special files are forbidden. Extraction requires a fresh immutable release directory; a duplicate remote dispatch fails instead of overwriting existing source. For a failed attempt, inspect SSM/host state and retry the reviewed host command against the preserved artifact under the filesystem lock.

## Optional OAuth buttons

Leave `NEXT_PUBLIC_OAUTH_PROVIDERS` blank in the `cloud-demo-publish` GitHub environment until OAuth is configured. Set it to `google`, `github`, or `google,github` to include the corresponding public provider names in the frontend build. The publication validator rejects unsupported names, duplicates and empty comma-separated entries. These names are public configuration; client secrets never enter build arguments.

Before enabling buttons, set protected runtime `AUTH_SPRING_PROFILES_ACTIVE=docker,cloud-demo,oauth2`, and supply both Google and GitHub `*_CLIENT_ID` / `*_CLIENT_SECRET` values through SSM `runtime.env`: the current backend OAuth profile declares both registrations. Register exact HTTPS callbacks `https://<approved-domain>/login/oauth2/code/google` and `https://<approved-domain>/login/oauth2/code/github` in their provider applications. Caddy and the gateway retain these routes, and trusted proxy handling supplies the public HTTPS origin. Publish a new immutable frontend release after changing the public names, then verify the actual provider callback and secure session flow in the authorized environment. Public OAuth remains NOT RUN until that verification occurs.

## Exact cloud and dependency CI gates

The `cloud-configuration` job runs deployment/backup contracts, `scripts/cloud/tests` (including actual HTTPS against a temporary local CA), effective cloud Compose policy tests, shell syntax for scripts/bootstrap files, Terraform fmt/init/validate and `terraform test` with mocked AWS, actual `caddy:2.11.7-alpine` configuration validation, and `prom/prometheus:v3.5.0` cloud configuration/rule validation. The local TLS transport test does not prove deployed OAuth, public certificates or a business journey. Caddy syntax validation performs no ACME certificate issuance. Terraform mocked plans never provision AWS resources. Each external validator has a fixed timeout, and the cloud job is bounded to 20 minutes.

The security job retains the complete `./mvnw -B -ntp -DskipTests verify -Psecurity-scan` gate. The current POM selects OWASP Dependency-Check 12.2.2 and fails at CVSS 9 or above; it does not claim that every lower-severity finding blocks publication. The profile uses the official NVD JSON2.0 bulk feeds with automatic updates and TLS validation. A missing/unavailable feed or scanner failure is a failed assessment, not a PASS. Secret/log-redaction checks and SBOM generation are distinct evidence and cannot establish a dependency vulnerability result. The actual local scan completed after switching from the failed anonymous API update and still fails on seven Spring findings, documented in [security review](cloud-security-review.md). Compatible public dependency updates reduced the original twenty threshold findings to seven; the owner chose to retain Boot3.5. No suppression or error/threshold bypass was added. Remote GitHub execution remains NOT RUN, and ECR publication will remain blocked by the enforced security gate. No API keys or vulnerability-feed credentials are printed by these commands.

Initial deployment has a separate manual `initial_demo_seed` boolean, default false, on the protected deploy workflow. Opting in permits only a first cloud-demo installation with no healthy release/recorded initial seed. The host passes explicit target and digest configuration to the guarded `--initial-only` seed after readiness and before the full journey; a conflicting existing synthetic account fails before promotion. See the first-install/partial-seed recovery steps in the deployment runbook.
