## B. Findings and fixes

### 1. CRITICAL — Paid inventory never committed or physically finalized

- **Affected modules:** inventory-service, order-service, event-contracts; payment consumer compatibility.
- **Root cause:** Payment success could request delivery without confirming durable inventory commitment. Reservations remained expirable and physical stock was not finalized by pickup.
- **Impact:** Paid orders could lose reserved stock; completed orders could leave reserved quantities indefinitely; later orders could oversell physical stock.
- **Files modified:** InventoryItem, InventoryReservation, ReservationStatus, InventoryWorkflowService, inventory Kafka configuration/listeners/application settings, OrderPaymentWorkflowService, OrderInventoryWorkflowService, order InventoryEventListener, payment OrderEventListener, EventType and two new V1 event records; inventory V3 migration; inventory consistency documentation. Exact paths are in H.
- **Fix:** Payment success emits `INVENTORY_COMMIT_REQUESTED`; inventory locks and commits the reservation and acknowledges `INVENTORY_COMMITTED`; only that acknowledgement requests delivery. `COMMITTED` does not expire. Pickup deducts on-hand and reserved quantities together and transitions to `FULFILLED`. Duplicate events cannot deduct again. Cancellation/failure before pickup releases committed quantities. Refunds after pickup do not restock physical goods. Unavailable commitment triggers financial compensation.
- **Tests added/updated:** InventoryFlowIT covers paid reservation expiry protection, duplicate pickup, release before pickup, and expired commitment compensation. InventoryCommitWorkflowTest covers the acknowledgement gate, duplicate acknowledgement, full refund before acknowledgement, and compensation. Event serialization cases include both new contracts.
- **Verification:** PASS in the full Java 21 build and real Compose journey. Stock moves from 10 on-hand/3 reserved to **7 on-hand/0 reserved/7 available**, and remains 7 after the completed-order refund.

### 2. HIGH — Outbox publishers could overtake earlier events for the same key

- **Affected modules:** inventory, order, payment, delivery, notification outboxes.
- **Root cause:** `FOR UPDATE SKIP LOCKED` prevented duplicate claims but allowed a different publisher to select later rows while an earlier row was in flight or waiting to retry. Timestamp/UUID ordering was insufficient.
- **Impact:** Cancellation, payment, fulfillment, and notification events could arrive in the wrong order.
- **Files modified:** All five OutboxStore classes and five append-only ordering migrations; transactional-outbox documentation; new OutboxOrderingIT.
- **Fix:** Add a database event sequence and select only the earliest unpublished row per `(topic, message_key)`. In-flight, retrying, or permanently failed head rows block later events for that key; other keys proceed in bounded batches. Existing retry and stale-claim recovery remain intact.
- **Tests added:** Three real PostgreSQL tests cover competing publishers/retries, independent keys, and expired claim recovery/ownership. The fixture upgrades order schema V4 to V5 with a pre-existing outbox row.
- **Verification:** PASS. Compose Kafka outage persisted publication retries; recovery drained the outboxes without unexpected DLT growth. Delivery remains at least once; no exactly-once claim is made.

### 3. HIGH — Early delivery cancellation could be lost; late cancellation could regress state

- **Affected modules:** delivery-service and order-service.
- **Root cause:** Cancellation arriving before delivery creation was marked processed without durable business intent. Creation/cancellation lacked protection for an absent delivery row. Cancellation-pending orders rejected legitimate in-flight progress events. Assigned-UUID JPA creation also ignored the managed return value.
- **Impact:** A refunded/cancelled order could later receive a delivery assignment; asynchronous progress could enter retry/DLT paths or leave inaccurate fulfillment state.
- **Files modified:** DeliveryWorkflowService, DeliveryRepository, new delivery V4 cancellation-tombstone migration, CustomerOrder, OrderDeliveryWorkflowService; DeliveryFlowIT and OrderDomainTest.
- **Fix:** Persist cancellation tombstones, serialize creation/cancellation with a transaction-scoped PostgreSQL advisory lock, lock existing deliveries, and mutate the managed saved entity. A later request creates a cancelled delivery and never assigns it. Late cancellation reconciles actual irreversible delivery state. Duplicate/stale progress cannot regress terminal fulfillment. Financial order state remains independent.
- **Tests added:** Real Kafka cancellation-before-creation test, concurrent two-delivery/one-agent assignment test, and cancellation/progress domain regressions.
- **Verification:** PASS. Successful delivery, failed delivery, cancellation races, agent release, and ownership checks pass.

### 4. MEDIUM — Retention cutoff could not bind correctly to PostgreSQL

- **Affected module:** scheduler-support and services using ConservativeRetentionJob.
- **Root cause:** Generic JDBC parameter binding passed `Instant` directly to PostgreSQL without an explicit SQL timestamp representation.
- **Impact:** Retention jobs could fail instead of cleaning old eligible records.
- **Files modified:** ConservativeRetentionJob and new ConservativeRetentionIT.
- **Fix:** Bind `Timestamp.from(cutoff)` while retaining bounded deletion predicates.
- **Test added:** Real PostgreSQL cleanup removes four eligible old rows and retains recent records, incomplete idempotency records, unpublished outbox work, and running job history.
- **Verification:** PASS. Existing concurrent scheduler lease and expired-lease recovery integration test also passes.

### 5. MEDIUM — Concurrent SSE registrations could exceed the per-user cap

- **Affected module:** notification-service.
- **Root cause:** List size checks, eviction, registration, removal, and connection gauge updates were not atomic.
- **Impact:** Concurrent connections could exceed five per user or produce inaccurate gauges/cleanup state.
- **Files modified:** SseRegistry and SseRegistryTest.
- **Fix:** Synchronize short registry mutations, send/complete outside the registry lock, handle disconnected emitters, and snapshot shutdown cleanup.
- **Test added:** 100 connections through 16 threads verify the five-connection cap, gauge, and shutdown cleanup.
- **Verification:** PASS. Authenticated live SSE connection and durable REST notification/read-unread behavior also pass; notification persistence does not depend on an active SSE client.

### 6. MEDIUM — GitHub could not discover nested workflows

- **Affected configuration:** CI and release workflows.
- **Root cause:** Workflows were under the Maven subdirectory instead of the Git repository's root `.github/workflows`; paths assumed Git and Maven roots were the same. CI omitted the existing master branch, and manual release input was not consistently used for identifiers.
- **Impact:** CI/release automation was not correctly discoverable for this repository layout.
- **Files modified:** Move CI/release YAML to root `.github/workflows`, update working directory, Maven cache/artifact/Docker context paths, branch triggers, and release identifier handling.
- **Verification:** Static YAML parsing and local build/configuration gates PASS. Remote GitHub Actions execution and release artifact upload are **NOT RUN** because this audit explicitly makes no commits or pushes.

### 7. MEDIUM — Kafka health checks could hang during outages

- **Affected modules:** inventory, order, payment, delivery, notification, operations.
- **Root cause:** Kafka metadata waits were unbounded in several indicators; default AdminClient closing could continue blocking after a bounded wait.
- **Impact:** Readiness/health requests could hang while Kafka was unavailable, reducing the usefulness of dependency monitoring.
- **Files modified:** KafkaConfiguration health indicators in the six modules.
- **Fix:** Three-second metadata deadlines, interrupted-thread preservation, and immediate AdminClient close in finally.
- **Verification:** PASS. Pausing the stack's Kafka produced bounded inventory readiness 503; unpausing recovered service communication and the durable payment workflow. All 44 final endpoint checks pass. This check does not establish that every indicator, including auth's existing cluster-ID indicator, detects every possible outage.

### 8. MEDIUM — Monitoring validation could pass without live coverage

- **Affected configuration:** API Gateway metrics, Prometheus configuration, monitoring/full-smoke scripts.
- **Root cause:** Registry was missing from the scrape list, HTTP histogram buckets needed by the gateway latency dashboard were not enabled, and static fallback could be presented as overall monitoring success.
- **Impact:** Incomplete visibility and misleading validation results.
- **Files modified:** Gateway application.yml, Prometheus configuration, validate-monitoring.sh, full-system-smoke-test.sh.
- **Fix:** Add registry scraping, enable gateway HTTP histogram buckets, require at least 11 healthy live targets and loaded healthy rule groups for the live check, and explicitly report live targets as NOT RUN in static-only mode. Full-system smoke requires live monitoring.
- **Verification:** PASS. All 11 targets have `up=1`; all eight rules load with health `ok`; gateway HTTP histogram and scheduler duration metric names exist; Grafana health reports database `ok`. Static dashboard JSON/datasource checks pass. No customer/order/product/payment/delivery IDs were added as metric tags.

### 9. LOW — Local startup and verification were unreliable on a small Docker host

- **Affected configuration:** 11 Dockerfiles, local Compose JVM options, .env.example, service-registry configuration, startup/smoke scripts.
- **Root cause:** Concurrent image builds and startup competed for memory/CPU; repeated dependency downloads and partial-image SBOM work increased build pressure. Local self-registry hostname was inconsistent with the Docker hostname. Some smoke HTTP calls lacked deadlines, and operations readiness was absent from the helper.
- **Impact:** Slow or timed-out startup/checks despite otherwise working services.
- **Fix:** Sequential service builds before startup, reusable Maven build cache, omission of aggregate SBOM generation only in partial image packaging, smaller local JVM settings with two active processors/C1 compilation, explicit registry hostname/default zone, operations readiness, and bounded HTTP calls. Production-like JVM configuration was not reduced. The final aggregate Maven verification still generated the full SBOM and ran all tests.
- **Files modified:** All service Dockerfiles, docker-compose.yml, .env.example, service-registry application.yml, dev-up.sh, smoke scripts.
- **Verification:** PASS. All 11 images built and dev-up completed. Final full-system smoke used a 600-second bounded polling budget and a 30-second individual request ceiling. An intermediate cold cart request exceeded an initial 10-second ceiling; a separate added smoke fixture used a stale cart version and correctly received 409. The deadline and fixture were corrected without changing business validation.
